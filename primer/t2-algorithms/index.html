Algorithms and data structures

Count the steps a program takes, and see which ones keep up as the data grows

An algorithm is a recipe a computer can follow, and a data structure is the way the data is laid out for that recipe. This chapter shows how to count steps. You will see why a dictionary finds a tag faster than a list and why sorting by merging beats sorting by inserting. You will also see why a model that compares all pairs of tokens gets expensive on long inputs.

The chapter ends with tracing a program by hand, line by line, and predicting the next value before you look. This habit makes you a better programmer and a better reader of code.

You will need: the lists, loops, functions and dictionaries of Python. Logarithms appear once, as "how many times can you halve n"; 0.3 covers them properly.

Stacks and queues

Guess first. You add the tags 4127, 3305 and 5519 to a pile, in that order, and then take two off. Which two come out, and in which order, if the pile is a stack? What if it is a queue?

stack
a pile where the last item added is the first one out (last in, first out)
queue
a line where the first item added is the first one out (first in, first out)
push, pop
add to the top of a stack; remove from the top
enqueue, dequeue
add to the back of a queue; remove from the front

A stack hands back the newest item first. A queue hands back the oldest item first.

The same tags go in, in the same order, and different tags come out. Remove two from the stack and two from the queue, and compare the two lines of output. You can add more tags too.

A stack is how an undo button works: the last thing you did is the first thing to undo. A queue is how a camera that sends frames to a model works: frames are processed in the order they arrive. Python's list is a good stack. For a queue use collections.deque, because taking the first item from a list makes all the others shift along, while a deque gives up its front item cheaply.

from collections import deque

stack = []
for tag in [4127, 3305, 5519]:
    stack.append(tag)            # push
print(stack.pop(), stack.pop())  # pop twice

queue = deque()
for tag in [4127, 3305, 5519]:
    queue.append(tag)            # enqueue
print(queue.popleft(), queue.popleft())  # dequeue twice
5519 3305
4127 3305

Trace six operations on the tags 4127, 3305, 5519 and 4635. The output shows both containers after the step. The stack gives back 5519 and then 4635, the newest items. The queue gives back 4127 and then 3305, the oldest.

A stack can also check that the brackets of a formula match. Push a bracket when it opens and pop when one closes. A closing bracket with an empty stack, or a non-empty stack at the end, means the brackets do not match.

def balanced(text):
    stack = []
    for ch in text:
        if ch == "(":
            stack.append(ch)          # push when a bracket opens
        elif ch == ")":
            if not stack:             # a closing bracket with nothing open
                return False
            stack.pop()               # pop when it closes
    return not stack                  # everything opened was closed

print(balanced("(w * (x + 1)) + b"))
print(balanced("(w * (x + 1) + b"))
print(balanced("w * x) + b"))
True
False
False

In practice: use a list as a stack and collections.deque as a queue. Taking the first item from a list moves all the other items along, so it slows down as the list grows. deque.popleft() takes the same time at any size.

Analogy. A stack is a pile of plates. You add and remove only at the top, so the plate you washed last is the first one back.

Where it breaks. You cannot reach into a pile of plates, but a Python list used as a stack lets you read or change any item by its index. Python does not enforce the stack rule. It is a habit in your code: use only append and pop.

Debug tip. Popping from an empty stack raises an IndexError. Test with if stack: before you pop.

Used in: recursion (below) works because Python keeps a stack of calls that are waiting for an answer. Backpropagation (B4) replays the steps of a forward pass newest first, as a stack hands items back. A data loader that feeds a model one batch after another behaves like a queue.

Quick quiz

Add A, B, C, then remove one, add D, then remove two. What comes out of a stack, and of a queue?

Stack: C, then D, then B. Queue: A, then B, then C. For the stack, after C leaves the pile is A, B, then D goes on top, and two pops give D and B.

What is left in the stack and in the queue at the end of the trace?

The stack has 4127 and 3305, with 3305 on top. The queue has 5519 and 4635, with 5519 at the front.

In the bracket check, what does a non-empty stack at the end tell you?

Some bracket was opened and never closed.

Lists and dictionaries for lookup

Guess first. You have 10,000 tags in a list and the same tags in a dictionary. You ask whether tag 14,100 is present. About how many tags does the list look at before it answers, and how many does the dictionary look at?

lookup
finding the stored value that belongs to a key
comparison
checking one stored item against the target; this chapter counts comparisons as steps
hash
a number computed from a key that says where its entry is stored
hash table
the structure behind Python's dictionaries and sets

A list finds an item by checking the items one by one. A dictionary computes where the item must be and goes straight there.

List size n

List: check one tag after another

0 comparisons

Dictionary: hash the tag, go to its slot

0 comparisons

A list needs about n/2 comparisons on average and the dictionary needs a little more than 1, however large n gets. Press Find a tag, then Run 1,000 lookups to average out the luck of a single target.

The dictionary in the figure is a small hash table. It turns a tag into a slot number with a formula, and two tags sometimes end up in the same slot. When that happens the slot keeps a short chain of tags and the lookup checks them. That is why the average is a little above 1. Python's dictionaries are built on the same idea. Its documentation lists a key lookup as constant time on average, with a worst case that grows with n if many keys collide.

tags = list(range(4101, 14101))          # 10,000 tags

def find_in_list(tags, target):
    comparisons = 0
    for t in tags:
        comparisons += 1
        if t == target:
            return comparisons
    return None

table = {t: i for i, t in enumerate(tags)}   # tag -> position
print(find_in_list(tags, 14100))
print(table[14100])
print(14100 in tags, 14100 in table)
10000
9999
True True

The last line looks the same for both, but in tags scans the list while in table is a lookup. The same is true for sets. Python's own documentation of its built-in types lists x in list as linear and x in set and a dictionary lookup as constant on average.

Build a toy hash table by hand with 8 slots. The slot of a tag is the remainder after dividing by 8. Tag 4127 gives 7, since 8 × 515 = 4120. Tags 3305, 5519 and 4635 give 1, 7 and 3. Tags 4127 and 5519 collide in slot 7, which keeps a short chain. Looking up 3305 makes one comparison and 5519 makes two. Looking up 4636 reaches the empty slot 4 and answers "not here" with none.

SLOTS = 8
table = [[] for _ in range(SLOTS)]
for tag in [4127, 3305, 5519, 4635]:
    table[tag % SLOTS].append(tag)      # the toy hash: tag mod 8
print(table)

def lookup(tag):
    comparisons = 0
    for t in table[tag % SLOTS]:
        comparisons += 1
        if t == tag:
            break
    return comparisons

print(lookup(3305), lookup(5519), lookup(4636))
[[], [3305], [], [4635], [], [], [], [4127, 5519]]
1 2 0

The slot is computed, not searched, so the cost does not depend on how many tags are stored while the chains stay short. Working tables grow as they fill. Python's own dictionary resolves a collision by probing other slots instead of keeping a chain, but the cost argument is the same. A key must give the same slot on all lookups, so it cannot change after it is stored. A dictionary also uses more memory than a list of the same keys, because it keeps empty slots.

In practice: when you test membership many times, use a set or a dictionary. To test many items against a long list, convert the list once with set(tags) and test against the set.

Common belief. Computers are so fast that the choice of list or dictionary does not matter.

Why it fails. It matters when a lookup happens millions of times on a large table. At a million entries a list scan makes about half a million comparisons, a dictionary about one. A single lookup is quick either way. A tokenizer that looks up a million words is not.

Better account. Judge a structure by how its cost grows with n, not by how fast one operation feels at the size you tried.

Used in: a tokenizer's vocabulary is a dictionary from token text to an integer ID, so turning a word into its ID does not scan fifty thousand entries (D1). The column names of a pandas table are keys in the same way.

Quick quiz

You need to test whether 5,000 tags appear in a log of 10 million tags. Do you loop over the log once per tag, or turn the log into a set first?

Build a set once, which costs about 10 million steps, then test the 5,000 tags at about one step apiece. Looping over the log once per tag costs up to 5,000 times 10 million steps.

How many comparisons does the toy table make for tag 5519, and why?

Two. The tag goes to slot 7, where 4127 is stored first, so the lookup checks 4127 and then 5519.

Building a set from a list of n tags takes about n steps. When is that cost worth paying?

When you test many items against the list. The set costs about n steps once, and then a test costs about one step instead of up to n.

Linear and binary search

Guess first. A sorted list has 1,000 lengths. You may ask questions of the form "is the target above the item at position p?". How many questions are enough to find any target for sure: about 10, about 100 or about 500?

linear search
check the items in order until you find the target
binary search
in a sorted list, check the middle item and discard the half that cannot contain the target
sorted
in increasing order; binary search needs this
\(\log_2 n\)
how many times you can halve n before 1 is left; \(\log_2 1024 = 10\)

Binary search needs a sorted list and finds any item in about \(\log_2 n\) steps. Linear search needs no order and may take n steps.

A step discards half of what is left, so the window shrinks 16, 8, 4, 2, 1 and the search ends in at most 5 steps for 16 items. Pick a target and press Step. Predict whether the next middle item will be above or below the target before you press.

The window is the stretch of positions that could still contain the target, from lo to hi. The middle position is mid. If the middle item is too small, all items at or below mid are too small and lo moves to mid + 1. If it is too large, hi moves to mid - 1. If lo passes hi, the window is empty and the target is not in the list.

A worked example with 1,000 items:

1,000items, n→9.97\(\log_2 n\)→10at most this many steps

\[ \text{steps} \le \lfloor \log_2 n \rfloor + 1 \]

  • \(n\) is the number of items in the sorted list.
  • \(\lfloor x \rfloor\) means round \(x\) down to a whole number. For \(n = 1{,}000\), \(\log_2 n \approx 9.97\), so the bound is \(9 + 1 = 10\).
  • Doubling \(n\) adds one step. A million items need at most 20 steps.
def binary_search(items, target):
    lo, hi = 0, len(items) - 1
    steps = 0
    while lo <= hi:
        mid = (lo + hi) // 2
        steps += 1
        if items[mid] == target:
            return mid, steps
        elif items[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return None, steps

def trace(items, target):
    lo, hi = 0, len(items) - 1
    step = 0
    while lo <= hi:
        mid = (lo + hi) // 2
        step += 1
        print(f"step {step}: lo={lo} hi={hi} mid={mid} items[mid]={items[mid]}")
        if items[mid] == target:
            print("found at", mid)
            return
        elif items[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    print("not found; lo =", lo, "above hi =", hi)

Binary search keeps one fact true: if the target is in the list, it lies between positions lo and hi. Discarding the half that cannot contain it keeps the fact true while the window halves. Halving n down to 1 takes about \(\log_2 n\) steps.

With repeated values the search may find either copy. bisect_left and bisect_right return the first position and the position after the last copy, so two searches count items in a range. Here 42.4 occupies positions 3 and 4, and 6 sharks lie between 40 and 50 cm.

lengths = [28.5, 36.1, 41.0, 42.4, 42.4, 44.0, 45.1, 46.0,
           52.0, 54.4, 62.2, 64.3, 74.5, 75.0, 82.0, 87.2]
print(bisect_left(lengths, 42.4), bisect_right(lengths, 42.4))
print(bisect_right(lengths, 50) - bisect_left(lengths, 40))

6

In practice: write the loop once to understand it, then use bisect. The usual mistakes are < against <= in the loop test and mid against mid + 1 in the update, which cause an endless loop or a missed item.

Common belief. Binary search is always faster than linear search.

Why it fails. Binary search needs a sorted list, and sorting costs about \(n \log_2 n\) steps. For one search in an unsorted list, a single pass of linear search is cheaper than sorting first.

Better account. Sort once and search many times, or keep the data in a dictionary. The cost of preparing the data belongs in the count.

Debug tip. Binary search on a list that is not sorted does not raise an error. It quietly returns a wrong answer. If a search misses something you can see, check the order first.

Quick quiz

What is the largest number of steps binary search needs on 1,000,000 items?

At most 20 steps. Since \(\log_2 1{,}000{,}000 \approx 19.93\), the bound \(\lfloor 19.93 \rfloor + 1\) is 20.

Why can binary search not be used on the unsorted list of lengths in tag order?

It relies on one fact: if the middle item is too small, so are all the items before it. That fact is false for an unsorted list, so it would discard the wrong half.

Why does the loop test use lo <= hi and not lo < hi?

When lo equals hi the window still contains one item, the last candidate. Stopping early would miss it, as in step 4 of the trace.

Sorting: insertion and merge

Guess first. Insertion sort and merge sort will race on the same 16 shark lengths, taken from the made-up catch table. Both count their comparisons. Which finishes with fewer, and by how much? What about for 1,000 sharks?

sort
put items in increasing order
insertion sort
take the next item and slide it left past larger items until it fits, like sorting a hand of cards
merge sort
split the list in halves, sort the two halves the same way, then merge the two sorted halves
merge
combine two sorted lists into one by repeatedly taking the smaller front item

Insertion sort takes up to about \(n^2/2\) comparisons, and merge sort takes about \(n \log_2 n\). The gap widens quickly as n grows.

Insertion sort

0 comparisons

Merge sort

0 comparisons

Merge sort finishes first on shuffled lengths, and insertion sort wins when the list is already almost in order. The 16 default lengths are sixteen records of the made-up catch table, in tag order. Watch where the two algorithms spend their comparisons: insertion sort slides one bar at a time, merge sort works on growing sorted blocks.

Insertion sort compares a bar with the one on its left and swaps while the left one is larger. On a reversed list all bars slide all the way, which is the worst case. On a nearly sorted list most bars need one comparison. Merge sort does not care about the order it starts in. It halves the list about \(\log_2 n\) times and one level of merging touches all n items once.

\[ C_{\text{insertion}} \le \frac{n(n-1)}{2}, \qquad C_{\text{merge}} \le n \lceil \log_2 n \rceil \]

  • \(C\) is the number of comparisons. \(n\) is the number of items.
  • Insertion sort's worst case is a reversed list: bar number \(i\) passes all \(i-1\) bars before it, and \(1 + 2 + \dots + (n-1) = n(n-1)/2\).
  • Merge sort's bound comes from about \(\lceil \log_2 n \rceil\) levels of merging, which use at most n comparisons apiece.
def insertion_sort(a):
    a = list(a)
    comparisons = 0
    for i in range(1, len(a)):
        j = i
        while j > 0:
            comparisons += 1
            if a[j - 1] > a[j]:
                a[j - 1], a[j] = a[j], a[j - 1]
                j -= 1
            else:
                break
    return a, comparisons

def merge_sort(a):
    if len(a) <= 1:
        return list(a), 0
    mid = len(a) // 2
    left, cl = merge_sort(a[:mid])
    right, cr = merge_sort(a[mid:])
    out, i, j, c = [], 0, 0, 0
    while i < len(left) and j < len(right):
        c += 1
        if left[i] <= right[j]:
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    out += left[i:] + right[j:]
    return out, cl + cr + c

The race and the code count the same way: one comparison whenever two lengths are compared. Python's own sorted uses an algorithm called Timsort, which takes advantage of any order already present in the data. For your own code, call sorted and keep the hand-written versions for learning.

Count by hand on the first four lengths, 42.4, 45.1, 74.5 and 41.0. Insertion sort compares 45.1 with 42.4 (1), then 74.5 with 45.1 (1), then slides 41.0 past 74.5, 45.1 and 42.4 (3). The total is 5. Merge sort sorts [42.4, 45.1] with 1 comparison and [74.5, 41.0] with 1. It then merges them by comparing 42.4 with 41.0, 42.4 with 74.5 and 45.1 with 74.5 (3). The total is also 5. For four items the two tie, and the gap opens as the list grows. On a shuffled list insertion sort falls between its best case, n − 1 = 15, and its worst, 120. The 16 lengths needed 60.

Python's sorted is stable: items with equal keys keep their earlier order. That makes two-pass sorts work. Sort by length first and by species second, and the lengths stay in order within a species. key= chooses what to sort on, and reverse=True flips the order.

In practice: to reorder one array by another, use np.argsort (0.1). To sort a list in place, call list.sort().

Common belief. Merge sort is always faster than insertion sort.

Why it fails. Big-O describes the worst case as n grows. On a list that is already in order, insertion sort needs only n - 1 comparisons, fewer than merge sort. For very short lists the extra bookkeeping of merging does not pay off.

Better account. Merge sort's cost barely depends on the input order, while insertion sort's depends on it heavily. That is why the winner changes with the data.

Quick quiz

For n = 1,000 reversed items, about how many comparisons does insertion sort need, and how many does merge sort need at most?

Insertion sort: 1,000 times 999 over 2, which is 499,500. Merge sort: at most 1,000 times 10, which is 10,000. The ratio is about 50.

The list is already sorted. How many comparisons does insertion sort make for n items?

n - 1. An item is compared once with its left neighbour, finds it smaller or equal, and stays.

Two sharks have the same length. After sorted(..., key=length), which comes first?

The one that came first in the input. Python's sort is stable, so ties keep their earlier order.

Top-k

Guess first. A model scores 50,000 possible next words and you want only the 5 best. Do you have to sort all 50,000 first?

top-k
the k items with the largest scores
scan
one pass over the items, looking at the items once
board
the short list of the k best items seen so far (a name used in this chapter)

To find the k largest of n items you need not sort all of them. Scan once and keep a board of the k best so far.

Comparisons so far: 0Full merge sort of these 16 would use: 0

After the board fills, most items fail the first check and cost one comparison. Slide k and press Step. Late items rarely enter the board.

For a vocabulary of n = 50,000 words and k = 50, the scan needs about 50,000 comparisons plus a few thousand to place the winners. A full sort needs about \(n \log_2 n \approx 780{,}000\). The scan wins because few items ever beat the weakest member of the board. Python's heapq.nlargest uses a smarter board called a heap, which keeps its weakest member at the front. Its documentation advises using sorted when k is large and max when k is 1.

import heapq

lengths = [42.4, 45.1, 74.5, 41.0, 36.1, 44.0, 64.3, 46.0,
           82.0, 28.5, 87.2, 42.4, 75.0, 62.2, 54.4, 52.0]   # cm, in tag order; made-up records

print(sorted(lengths, reverse=True)[:3])
print(heapq.nlargest(3, lengths))

def top_k(items, k):
    board, comparisons = [], 0        # the board: the k best so far, largest first
    for x in items:
        if len(board) == k:
            comparisons += 1
            if x <= board[-1]:         # not above the weakest board item
                continue
            board.pop()
        i = len(board)
        while i > 0:                  # find the place for x
            comparisons += 1
            if board[i - 1] >= x:
                break
            i -= 1
        board.insert(i, x)
    return board, comparisons

print(top_k(lengths, 3))

([87.2, 82.0, 75.0], 25)

The order of arrival matters. In increasing order a new item always beats the weakest and must be placed: 42 comparisons for these 16. In decreasing order only the first three enter: 15 comparisons. In random order item \(i\) enters with probability \(k/i\), because it must be among the best \(k\) of the first \(i\). Summing \(k/i\) from \(i = k + 1\) to \(n\) gives about \(k \ln(n/k)\) entries after the first \(k\). For \(n = 50{,}000\) and \(k = 50\) that is about 50 + 345 = 395 entries. One random run varies around that figure: this one gave 375.

In practice: top-k sampling for text keeps the k best scores and rescales them to sum to 1 (D3). Take made-up probabilities 0.55, 0.30, 0.10, 0.04 and 0.01 with k = 2. The kept ones sum to 0.85, so they become 0.55 / 0.85 = 0.65 and 0.30 / 0.85 = 0.35.

Common belief. To find the best few items you must sort all of them.

Why it fails. A scan with a board of k places needs about n comparisons when k is small, and a full sort needs about \(n \log_2 n\). Most of the sorting work orders items that you never use.

Better account. Keep a board when you want only the best few. Sort when you want the whole order, or when k is close to n.

Debug tip. Check the cases at the edges: k larger than the list, and ties. With k = 20 and 16 items, sorted(...)[:20] quietly returns all 16, while code that assumes k items may fail.

Used in: a language model scores all the words in its vocabulary for the next position. Top-k sampling keeps the k highest scores and draws the next word from those only (D3).

Quick quiz

Why does the scan with a board cost about n comparisons and not n times k?

Most items are smaller than the weakest board member, so one comparison rejects them. Only a few items enter the board, and only those pay for placing themselves among the k members.

In which order should the data arrive to make the board scan as slow as possible?

Increasing order. A new item always beats the weakest board member, so it enters the board and must be placed.

Recursion and trees

Guess first. A function total(n) returns n + total(n - 1), and total(0) returns 0. What is total(4)? What happens if you forget the rule for 0?

recursion
a function that calls itself on a smaller version of the problem
base case
the smallest case, answered directly so the calls stop
call stack
the stack of calls waiting for an answer from the call above them
tree
a graph with one root and no loops, here a call tree (a reminder; 0.4 defines graphs); a leaf is a node with no children

A recursive function solves a problem by solving a smaller copy of it, and it stops at a base case.

Call stack

Calls made so far: 0Deepest stack: 0Answer: ?

The call stack grows by one frame per waiting call, and answers come back up in the reverse order of the calls. Choose total, step through, and then try fib to see a function that calls itself twice.

The function total(4) waits for total(3), which waits for total(2), and so on down to the base case total(0). Then the answers return one by one: 0, 1, 3, 6, 10. The call stack is a stack in the sense of the first section.

def total(n):
    if n == 0:                 # base case
        return 0
    return n + total(n - 1)    # a smaller copy of the problem

Trees are recursive too: a tree is a root with smaller trees hanging from it. A decision tree answers a question about a shark by testing one feature and then handing the shark to the smaller tree on the chosen side. The toy tree below is made up for this figure.

def predict(node, shark):
    if "leaf" in node:                         # base case
        return node["leaf"]
    feature, cut = node["test"]
    branch = "yes" if shark[feature] < cut else "no"

Recursive functions fit recursive data. To count the leaves of the toy tree, a leaf counts as 1 and any other node adds the counts of its two sides. The depth follows the same pattern: a leaf has depth 0 and any other node is 1 deeper than its deeper side. The toy tree has 3 leaves, and its longest path has 2 tests.

def count_leaves(node):
    if "leaf" in node:                  # base case
        return 1
    return count_leaves(node["yes"]) + count_leaves(node["no"])

def depth(node):
    if "leaf" in node:
        return 0

Common belief. A function that calls itself is just as cheap as the loop version.

Why it fails. When a function calls itself twice, it can repeat the same work many times. The naive fib in the figure computes fib(2) again and again, and the count of calls explodes.

Better account. Count the calls, not the lines of code. A dictionary that stores the answers the first time removes the repeats.

calls = 0
def fib(n):
    global calls
    calls += 1
    return n if n < 2 else fib(n - 1) + fib(n - 2)

print(fib(20), calls)

memo, calls2 = {}, 0

    calls2 += 1

        return memo[n]
    memo[n] = n if n < 2 else fib_memo(n - 1) + fib_memo(n - 2)

The explosion of fib has a formula. Let \(c(n)\) be the number of calls that fib(n) makes. Then \(c(0) = c(1) = 1\), and for larger \(n\) the call counts itself plus the calls of its two children: \(c(n) = 1 + c(n-1) + c(n-2)\). This gives 1, 1, 3, 5, 9, 15, 25 for \(n\) from 0 to 6, as the output below shows. It matches \(c(n) = 2\,\mathrm{fib}(n+1) - 1\), so \(c(20) = 2 \times 10{,}946 - 1 = 21{,}891\). The calls grow like the Fibonacci numbers, about 1.6 times larger when \(n\) grows by 1.

Quick quiz

What are the two parts a recursive function needs?

A base case that returns an answer without another call, and a recursive case that calls the function on a smaller input, so the calls move toward the base case.

In predict, which line is the base case?

The line that tests "leaf" in node and returns the label. A leaf has no smaller tree to hand the shark to.

It makes 9 calls, from the table: 1, 1, 3, 5, 9 for n from 0 to 4.

Big-O: steps against size

Guess first. A program does 1,000 steps on an input of 1,000 items. If the input doubles to 2,000 items, how many times as many steps will it do if its cost grows like n? Like n squared? Like \(\log_2 n\)?

Big-O
how the number of steps grows with the input size n, ignoring constant factors and smaller terms
\(O(1)\)
constant: the steps do not grow with n
\(O(\log n)\)
logarithmic: doubling n adds one step; binary search
\(O(n)\)
linear: doubling n doubles the steps; a scan
\(O(n \log n)\)
a little worse than linear; merge sort
\(O(n^2)\)
quadratic: doubling n quadruples the steps; insertion sort's worst case, comparing all pairs

Big-O describes how the step count grows as n grows. Doubling n doubles \(O(n)\), roughly doubles \(O(n \log n)\), quadruples \(O(n^2)\) and adds one step to \(O(\log n)\).

Axes

For small n the curves lie close together, and beyond a few hundred items the n squared curve leaves the others behind. Raise the constant factor on the n log n curve and the curves cross much later.

The step counts here are formulas with a constant factor in front: the n log n algorithm uses \(c \cdot n \log_2 n\) steps and the other algorithms use one step per unit. Big-O drops the constant \(c\), but the constant decides who wins for small n. In the figure, move the constant to 20 and find the size where the n squared curve first rises above the n log n curve.

Big-O also drops smaller terms. A program that makes \(3n^2 + 5n + 2\) steps is \(O(n^2)\), because at large n the \(5n\) and 2 are a tiny share of the total. The boxes below use the n you set in the figure.

\[ T(n) = 3n^2 + 5n + 2 = O(n^2) \]

  • \(T(n)\) is the number of steps the program takes on an input of size \(n\).
  • \(O(n^2)\) says that for large \(n\), \(T(n)\) is at most a constant times \(n^2\). The constant 3, the \(5n\) and the 2 are not part of the label.
import random
random.seed(1)

def comparisons(n):
    a = [random.random() for _ in range(n)]
    lin = 0                                 # linear search for the last item
    for x in a:
        lin += 1
        if x == a[-1]:
            break
    b, ins = list(a), 0                     # insertion sort
    for i in range(1, n):
        j = i
        while j > 0:
            ins += 1
            if b[j - 1] > b[j]:
                b[j - 1], b[j] = b[j], b[j - 1]
                j -= 1
            else:
                break
    def ms(x):                              # merge sort
        if len(x) <= 1:
            return x, 0
        m = len(x) // 2
        l, cl = ms(x[:m])
        r, cr = ms(x[m:])
        out, i, j, c = [], 0, 0, 0
        while i < len(l) and j < len(r):
            c += 1
            if l[i] <= r[j]:
                out.append(l[i]); i += 1
            else:
                out.append(r[j]); j += 1
        return out + l[i:] + r[j:], cl + cr + c
    _, mrg = ms(a)
    return lin, ins, mrg

prev = None
for n in (100, 200, 400, 800):
    lin, ins, mrg = comparisons(n)
    ratio = "" if prev is None else f"  x{ins / prev[0]:.1f} {mrg / prev[1]:.1f}"
    print(n, lin, ins, mrg, ratio)
    prev = (ins, mrg)

The last two numbers on a line show what happened to insertion sort and merge sort when n doubled. Insertion sort's count roughly quadrupled whenever n doubled. Merge sort's roughly doubled, slightly more. That is what \(O(n^2)\) and \(O(n \log n)\) predict, observed without a stopwatch.

Count the steps of code with three rules. A loop over n items costs n steps. A loop inside a loop costs n times n. A step that halves the problem costs about \(\log_2 n\). Steps one after another add, and the largest term wins. The block prints the counts for n = 1,000.

for x in range(n):                 # one pass over n items
    steps["one pass"] += 1
for x in range(n):                 # a pass inside a pass
    for y in range(n):
        steps["pass inside pass"] += 1
m = n
while m > 1:                       # halve until one is left
    m = m // 2
    steps["halving"] += 1

Scale this up to a million records. In the worst case, a list in reverse order, insertion sort needs about \(n(n-1)/2 \approx 5 \times 10^{11}\) comparisons. Merge sort needs about \(n \log_2 n \approx 2 \times 10^{7}\) comparisons. Suppose a program makes \(10^7\) comparisons per second, an assumed round number for plain Python. Insertion sort then needs about 14 hours and merge sort about 2 seconds. The ratio, about 25,000, matches \(n / (2\log_2 n)\).

import math

merge = n * math.ceil(math.log2(n))
speed = 10_000_000                 # comparisons per second: an assumed round number

In practice: Big-O guides the choice and a measurement settles it. Time the program on your own data with time.perf_counter, because constants matter at small n. Profile before you optimise, since the slow line is often not where you expect.

Common belief. An \(O(n)\) program is always faster than an \(O(n^2)\) one, and Big-O says how long a program takes.

Why it fails. Big-O ignores constants, the machine and the input. A program with \(100n\) steps is slower than one with \(n^2\) steps for all n below 100.

Better account. Big-O says how the cost grows. It tells you which program will win for a large enough n, and when to expect trouble if the input gets bigger.

Now the case that matters most for the rest of this primer. A language model reads a prompt of n tokens. Self-attention compares all tokens with all the other tokens, so it forms about \(n^2\) pairs. Vaswani and colleagues list the cost of a self-attention layer as \(O(n^2 \cdot d)\), where \(d\) is the size of the vectors, in Table 1 of the paper that introduced the Transformer.

A prompt ten times longer makes a hundred times as many pairs. Slide n and compare the pair count with that of a 1,000-token prompt, which has a million pairs.

Memory grows with the pairs too. Take \(n = 10{,}000\) tokens. A full table of attention scores has \(n^2 = 10^8\) numbers. At 4 bytes per number that is 400 MB for one head in one layer, if stored in full. This is why long inputs need the methods of D6.

Used in: the \(n^2\) growth of attention is why long prompts are expensive, and why D6 studies variants that look at a window or a summary instead of all pairs. The same step-counting habit appears in B8, where the update-to-weight ratio shows how many steps a layer needs to change by its own size.

Quick quiz

An algorithm takes 3 seconds for n = 1,000 and is \(O(n^2)\). About how long for n = 4,000?

About 48 seconds. Quadrupling n multiplies the steps by 16, and 3 times 16 is 48. The constants cancel in the ratio, which is why Big-O is useful for predictions.

Which grows faster, \(100\, n \log_2 n\) or \(n^2\)?

\(n^2\) eventually, but only from n = 997 onward. Below that, the \(100\, n \log_2 n\) program takes more steps.

A loop over n items makes one dictionary lookup in the body. What is the Big-O of the loop?

\(O(n)\). The loop makes n passes, and a dictionary lookup costs about one step.

A pandas filter such as df[df["length_cm"] > 60] touches all rows. How does its cost grow with the number of rows, and what does that say about filtering 10 million rows twice?

It grows in proportion to the number of rows, so it is \(O(n)\). Two filters cost about twice one filter, which is acceptable. The chapter on Python described the mask the filter builds.

Why does a dictionary need keys that cannot change, and how does that connect to hashing?

The dictionary computes a slot from the key. If a key changed afterwards, its slot would change and the entry could not be found. Tuples and strings never change, so Python allows them as keys; lists can change, so it refuses them.

Binary search on 1,000,000 sorted items takes at most 20 steps. What would the same count be for a linear search, and what is the ratio?

Linear search may need up to 1,000,000 steps, so the ratio is 50,000. A million items is no harder for binary search than 20 steps, which is the whole value of keeping data sorted.
