Debugging neural networks

A routine, a lab of broken runs and the numbers that say which part is at fault

A network that trains badly gives you one number, the loss, and that number rarely says what is wrong. A flat loss can come from six different faults. This chapter gives a routine in the spirit of Andrej Karpathy's recipe and Andrew Ng's advice. Look at the data, set a baseline, check the starting loss, overfit one small batch, then add one thing at a time.

The core is a lab of six broken runs on the made-up SharkCam catch records. You pick a symptom, read the loss, the gradient norm of the layers and the update-to-weight ratio, and try fixes. The chapter then covers gradient clipping, a learning-rate range test, and learning curves with bias and variance. It ends with reproducibility and a pipeline with four bugs that you find by testing one component at a time.

You will need: vanishing and exploding slopes (B4), learning rates and Adam (B5), initialisation and normalisation (B6), validation sets and overfitting (A4) and the confidence interval (0.7).

The routine and the starting loss

Guess first. A network will sort sharks into five species. Before any training step, with random weights, you compute the loss on one batch. About what should it be: 0, 0.5, 1.6 or 5?

baseline
a simple model whose score the network must beat (the lazy model of A4)
starting loss
the loss on a batch before any step
overfit one batch
train on 16 sharks until the loss is near 0, as a test of the whole training loop
error analysis
reading the cases the model gets wrong, to see what kind of data or change would help

Most bugs are found by checking small things in a fixed order, with a number you know before you look.

The seven checks have expected numbers, and a check that fails points at one part of the system. The order runs from cheap and general (the data) to expensive and specific (tuning).

The routine follows Karpathy's "A Recipe for Training Neural Networks" (2019). It asks you to start by inspecting the data, before any network code. Then you build a complete training and evaluation loop with dumb baselines, and overfit before you regularise. The routine also follows Ng's Machine Learning Yearning. Its chapter 13 advises building a first system quickly and iterating. Its chapter 14 shows how to read the dev set examples that a system gets wrong. Both the recipe and the Stanford CS231n notes list the two sanity checks, the starting loss and a tiny training set. The update-to-weight ratio of the next sections comes from the CS231n notes.

The answer to the guess is 1.6. With random weights the network gives all five species about the same probability, 1/5, so the log loss is \(-\ln(1/5) = \ln 5 = 1.609\). The CS231n notes make the same check for ten classes: \(\ln 10 = 2.30\). A second number is worth knowing for this data. A model that has learned only the shares of the species in the table (45%, 33%, 12%, 9.5% and 0.5%) gets a loss equal to the entropy of the labels. That is \(-\sum p\ln p = 0.36 + 0.37 + 0.25 + 0.22 + 0.03 = 1.23\). A flat loss at 1.23 means a network that knows the base rates and no more.

If the output scores start at size 0.1 the first loss is 1.61. If they start at size 2 it is 2.8, and at size 5 it is 6.0. A first loss far above 1.6 says that the last layer starts too large. Simulated with 40,000 draws of five random scores and a random correct class.

\[ L_0 \;=\; -\ln\frac{1}{K} \;=\; \ln K \]

  • \(L_0\) is the cross-entropy loss before training. \(K\) is the number of classes, 5 for the species.
  • The formula assumes that the scores are all close to 0, so softmax gives all classes the probability \(1/K\) (0.7). The figure shows what happens when they are not.

Why the loss grows with the score size. Let the five starting scores be random with spread \(s\) around 0. For small \(s\), expand \(\ln\sum_k e^{z_k}\) to second order. It is \(\ln K + \bar z + \tfrac12\,\mathrm{var}(z)\), where \(\bar z\) is the mean of the \(K\) scores of a shark and \(\mathrm{var}(z)\) their variance across the classes. The loss of a shark is this minus the score of its true class. That score has mean 0, and the variance across classes averages \(s^2(1 - 1/K)\). So the loss is about \(\ln K + \tfrac12 s^2(1 - 1/K)\), which is \(1.609 + 0.4\,s^2\) here. For large \(s\) the largest score dominates, and the loss is about the gap between the largest of five random scores and the score of the true class. That gap averages \(1.16\,s\). The simulation is close to the first line up to \(s = 0.5\) and to the second only for large \(s\). At \(s = 0.1\) the first gives 1.613 against a simulated 1.614. At \(s = 5\) the second gives 5.8 against 6.0. At \(s = 2\) the simulation, 2.80, lies between the two formulas (3.21 and 2.32).

import numpy as np

rng = np.random.default_rng(0)

    small = np.log(K) + 0.5 * s**2 * (1 - 1 / K)              # formula for small s
    print("s = %.1f  simulated %.3f  small-s formula %5.3f  large-s formula %.2f" % (s, loss.mean(), small, 1.16 * s))

The code also prints the loss of a network that knows only the species shares: 1.231, the entropy of the labels. The same check for a regression. A network whose outputs are near 0 starts with a mean squared error equal to the mean of the squared targets. For the weights of all 600 made-up sharks that is 19.1 kg\(^2\). The code of the clipping section prints 5.70 for 32 ordinary sharks and 346.83 for the 32 heaviest. The mean squared weights of those two groups are 5.3 and 344.7, so the printed losses are what an untrained network with outputs near 0 must show.

Where it misleads. A correct starting loss does not mean the network is right. In the last section a pipeline with three bugs has a starting loss of 1.613 against \(\ln 5 = 1.609\). The check catches a narrow set of faults: a wrong loss function, an output layer that starts large, inputs that are not scaled (the lab's first loss of 9.1). In practice, run it whenever you change the loss, the output layer or the number of classes, and write the expected value next to the printed one.

Debug tip. If the starting loss is much lower than \(\ln K\), look for label leakage, because a network that starts far below chance can usually see the answer. If it is far above, look at the last layer's size and at the input scale.

Quick quiz

A network with 10 classes starts with a loss of 2.3, and one with 1,000 classes. What should the second show?

\(\ln 1000 = 6.91\). A loss of 2.3 there would mean the output is already far from uniform.

Why try to overfit 16 sharks before training on 480?

On 16 sharks a correct loop can reach a loss near 0, because the network has far more weights than examples. If it cannot, the fault is in the model, the loss or the update step, and it is easier to find on 16 examples than on 480.

A 5-class network starts at a loss of 2.8 on the species problem. Roughly how large are its output scores?

Their spread is about 2. The simulation gives 2.80 for \(s = 2\), against \(\ln 5 = 1.61\) for scores near 0. The last layer starts too large, or the inputs are not scaled.

The broken-run lab

Guess first. A training run ends with the loss at 1.23 and a validation accuracy of 48%, the same as the lazy model. How many different faults can produce that picture: one, two, or three or more?

symptom
what you see in the logs
cause
the fault behind it, which you can only test by changing one thing
dead unit
a ReLU unit that outputs 0 for all training examples, so its slope is 0 and it cannot recover (B1)
layer norm of the gradient
the size of the loss slope on all weights of one layer, written \(\lVert g\rVert\) (B4)

Several faults give one symptom, and the curves inside the training loop, which are cheap to log, tell them apart.

The final loss 1.2 appears in three runs for three different reasons. One has gradients near 1e-6 in the early layers (bad initialisation). One has gradients of 0 after a normal start (dead ReLUs). One has gradients of 0 after a start at 9.1 (raw inputs). The network has four hidden layers of 24 units, trained on 480 made-up catch records with SGD and momentum 0.9; the regression run predicts weight in kg. One seed per run, so differences of a few points in accuracy are noise.

Work through the six symptoms. For a symptom, look first at the loss and its first value. Then look at the gradient plot (a line is missing where the norm is 0), the update ratio and the dead-unit bars. Choose a diagnosis before you try a fix, then test it. A fix that works is evidence for a cause. A fix that changes no result is evidence against one. The lab also has fixes that look good and are not. Adam rescues the badly initialised network, but the cause is still there. A lower rate rescues the raw-input run (74%) but the first loss is still 9.1.

The answer to the guess is three or more, and the lab shows three. Bad initialisation, raw inputs, and dead ReLUs after a learning rate of 0.5 all end near 1.23. This is why a rule such as "when training fails, lower the learning rate" does poorly. In this lab a lower rate fixes the NaN run and the dead-unit run, hides the raw-input problem, and leaves the shuffled labels and the exploding gradients as they were.

A diagnosis by numbers. Take the badly initialised run. Its loss starts at 1.61, which is right, and ends at 1.24 with a validation accuracy of 48.3%, the lazy model. The gradient plot shows norms of about \(5\times10^{-7}\) in layers 1 to 3, and the update ratio of layer 1 is \(4\times10^{-7}\). The code below shows what the network learned. The spread of its output scores across the sharks is 0.0000 for all five species. The last-layer bias equals the log of the class share plus a constant, which is 2.1 to 2.2 for four species and 2.9 for the rarest. The softmax ignores a constant, so the biases alone say "45% spadenose, 33% milk, 12% bamboo" and so on. The network learned the base rates in its last bias and made no use of the inputs. A loss stuck at 1.23 is the sign of a network that has stopped using its inputs.

The raw-input run has a different story behind the same end. Its first loss is 9.14, and its output scores have a spread of 22, against 0.8 for the standardised inputs. At a rate of 0.05 the first step changes layer 1 by 11% of its size (gradient norm 13.8, weight norm 6.4). That is about 50 times the 0.002 of the standardised run at the same rate. By the end, 96% of the units in layer 1 are dead. The dead-unit run has a third story. Its loss starts at 1.48, its rate is 0.5, and at the end all the units of layers 3 and 4 are dead.

species = ["spadenose", "milk", "bamboo", "hammerhead", "ganges"]
cols = ["length_cm", "weight_kg", "girth_cm", "depth_m", "temp_c", "month"]
X = np.array([[r[c] for c in cols] for r in rec], dtype=np.float32)
y = torch.tensor([species.index(r["species"]) for r in rec])
p = np.random.RandomState(0).permutation(len(rec)); tr, va = p[:480], p[480:]       # 480 for training, 120 for validation
X_raw = torch.tensor(X)
X_std = torch.tensor((X - X[tr].mean(0)) / X[tr].std(0))

def network(spread=None, seed=0):                 # four hidden layers of 24 ReLU units
    torch.manual_seed(seed)
    net = nn.Sequential(nn.Linear(6, 24), nn.ReLU(), nn.Linear(24, 24), nn.ReLU(),
                        nn.Linear(24, 24), nn.ReLU(), nn.Linear(24, 24), nn.ReLU(), nn.Linear(24, 5))
    lins = [m for m in net if isinstance(m, nn.Linear)]
    for k, m in enumerate(lins):
        fan_in = m.weight.shape[1]
        std = spread or math.sqrt((1 if k == len(lins) - 1 else 2) / fan_in)    # He, or one fixed spread
        nn.init.normal_(m.weight, 0, std); nn.init.zeros_(m.bias)
    return net

def first_look(name, net, X):
    """Numbers to read before the first update."""
    loss = nn.functional.cross_entropy(net(X[tr]), y[tr])
    net.zero_grad(); nn.functional.cross_entropy(net(X[tr[:32]]), y[tr[:32]]).backward()
    g = [m.weight.grad.norm().item() for m in net if isinstance(m, nn.Linear)]
    print(f"{name:17s} start loss {loss.item():5.2f}  gradient norms", " ".join("%.0e" % v for v in g))

first_look("spread 0.005", network(spread=0.005), X_std)

Common belief. If the loss does not fall, the learning rate is wrong, so lower it.

Why it fails. Of the six faults in the lab, a lower rate fixes two, hides a third, and leaves two more as they were. Labels that do not match their rows and exploding gradients are untouched by a smaller rate. For the bad starting scale the lab offers a higher rate, which makes it worse.

Better account. The loss tells you that something is wrong. The gradient norms, the update ratio and the dead-unit count tell you where. Change one thing, then look again.

Debug tip. Change one thing at a time. The lab lets you switch on two fixes together, and the result can hide which of them did the work. In the NaN run, clipping alone and a wider network alone both fail, but together they train.

Gradient norms and the update-to-weight ratio

Guess first. In a five-layer network the gradient norm is 6e-7 in layer 1 and 2e-2 in layer 5. The loss is falling a little. Is the network fine, or is there a problem with the early layers?

gradient norm
\(\lVert g\rVert = \sqrt{\sum_j g_j^2}\) over the weights of a layer: one number for how steep the loss is for that layer
update-to-weight ratio
the size of the change a step makes to a layer divided by the size of the layer's weights
histogram over time
the distribution of gradients or activations in a layer, drawn at intervals during training

A layer learns at a sensible speed when one step changes it by about a thousandth of its size. Layers whose steps differ by a factor of a million are not learning together.

At rate 0.02, gradient norm 1 and weight norm 10, a step changes the layer by 0.2% of its size, inside the usual range. The calculator is the formula for plain SGD without momentum; the lab's runs use momentum 0.9, which makes the steady step up to ten times larger.

The answer to the guess is "a problem". The numbers are from the badly initialised run of the lab. The gradient norm of layer 1 is 5.8e-7 and its update ratio is 3.7e-7. At that speed the layer needs 1/(3.7e-7), about 2.7 million steps, to change by its own size. Layer 5, at 0.005, moves more than 10,000 times faster. In a healthy run of the same network the gradient norms of the five layers stay between about 0.4 and 1.5, with a median near 0.7. The ratios have a median near 0.0035. The picture of the slopes sent back and multiplied layer by layer is the one of B4, and B6 shows how the starting scale decides it.

The ratio is a rule of thumb from the CS231n notes, which suggest about \(10^{-3}\). A lower ratio can mean that the learning rate is too low, and a higher one that it is probably too high. The rule depends on the optimiser. For plain SGD the step is \(\eta\,g\), so the ratio is \(\eta\lVert g\rVert/\lVert\theta\rVert\). For Adam the step of a weight is about \(\eta\) whatever its slope (B5). The ratio then depends on \(\eta\) and the weight sizes, and you should look for a layer that is far from the others. In practice, log the gradient norm and the ratio of the layers at intervals of 50 to 100 steps and plot them on a log axis. Compare layers with one another and with their own past. A sudden change in one layer is a better clue than any absolute number.

\[ r \;=\; \frac{\lVert \Delta\theta\rVert}{\lVert\theta\rVert} \;=\; \frac{\eta\,\lVert g\rVert}{\lVert\theta\rVert} \quad\text{(plain SGD)} \]

  • \(r\) is the update-to-weight ratio of one layer. \(\Delta\theta\) is the change of the layer's weights in one step and \(\theta\) the weights themselves, with the norm taken over the whole layer.
  • \(\eta\) is the learning rate and \(g\) the gradient of the layer. With momentum \(\beta\) the steady step is up to \(1/(1-\beta)\) times larger, which is 10 times for \(\beta = 0.9\). The lab's logged values are 2 to 10 times the plain formula.

The two boxes above are worked examples with numbers from the lab. The plain formula gives 0.0017 for the healthy layer, and the logged value is 0.0032, about 2 times higher because of momentum. For the badly initialised layer, whose weights have spread 0.005 and so a norm of only 0.06, the formula gives 1.9e-7 and the log says 3.7e-7. What matters is the gap between the two layers: a factor of about 10,000.

The ratio under Adam. At its first step Adam moves a weight with slope \(g\) by \(\eta\,g/(\lvert g\rvert + \epsilon)\), where \(\epsilon\) is 10\(^{-8}\). Later steps use running averages in place of \(g\), and no step is much larger than \(\eta\). When \(\lvert g\rvert\) is far above \(\epsilon\), all weights move by about \(\eta\) at the first step. A layer of \(n\) weights then moves by \(\eta\sqrt n\) and has a norm of \(\sqrt n\,\bar w\), so \(r \approx \eta/\bar w\). Here \(\bar w\) is the root mean square weight. For later steps this is a ceiling. With \(\eta = 0.01\) and the lab's healthy first layer (\(\bar w = 0.54\)) it gives 0.019. The lab's run with He initialisation and Adam logs 0.019 at step 1 and about 0.004 near the end, when the slopes of different batches disagree. The bad start breaks the condition. In the lab's Adam run from the bad start (rate 0.01) the first-layer slope at step 1 is about \(3.6\times10^{-9}\) per weight, below \(\epsilon\). The step is only 26% of \(\eta\), and the ratio is 0.53, near the 0.46 that was logged. At step 2 the logged ratio is 0.83. Plain SGD in the same start had a ratio of \(10^{-8}\). Adam rescues the run because its step does not shrink with the slope until the slope falls below \(\epsilon\).

# continues the lab code above
def log_run(net, X, lr=0.02, steps=375):
    opt = torch.optim.SGD(net.parameters(), lr=lr, momentum=0.9)
    lins = [m for m in net if isinstance(m, nn.Linear)]
    g = torch.Generator().manual_seed(0); norms, ratios = [], []
    for _ in range(steps):
        i = torch.tensor(tr)[torch.randint(0, 480, (32,), generator=g)]
        before = [m.weight.detach().clone() for m in lins]
        opt.zero_grad(); nn.functional.cross_entropy(net(X[i]), y[i]).backward()
        norms.append([m.weight.grad.norm().item() for m in lins])
        opt.step()
        ratios.append([((m.weight.detach() - b).norm() / b.norm()).item() for m, b in zip(lins, before)])
    return np.array(norms), np.array(ratios)

for name, net in [("He", network()), ("spread 0.005", network(spread=0.005))]:

    print("%-12s median gradient norm" % name, " ".join("%.0e" % v for v in np.median(n, 0)))
    print("%-12s median update ratio " % name, " ".join("%.0e" % v for v in np.median(r, 0)))

Quick quiz

Rate 0.01, gradient norm 2, weight norm 40. Plain SGD. What is the ratio and is it in the usual range?

\(0.01 \times 2/40 = 5\times10^{-4}\). That is a little below \(10^{-3}\), so the layer moves slowly, though still within a factor of 2 of the usual value.

Why can gradient norms of different layers differ by 10 times in a healthy network?

Layers have different sizes and different weight norms. A comparison of layers is meaningful in the ratio of step to weight, which divides out the size, more than in the raw norm.

Adam with \(\eta = 0.001\) trains a layer whose typical weight is 0.05. What ratio do you expect, and is it in the usual range?

\(r \approx \eta/\bar w = 0.001/0.05 = 0.02\) at most. That is up to 20 times the usual \(10^{-3}\), so the layer may move fast. Log the ratio to see, then lower the rate or check why the weights are so small.

Gradient clipping

Guess first. One batch of sharks gives a gradient that is 20 times larger than usual. You rescale it so that its length is 1. Does the weight update still point the same way?

gradient clipping by norm
if the gradient's length is above a threshold \(c\), shrink it to length \(c\) and keep its direction
clipping by value
limit all components to \([-c, c]\) separately, which can change the direction
exploding gradient
a gradient so large that one step wrecks the weights (B4)

Clipping by norm caps the size of a step and keeps its direction, which stops one extreme batch from rewriting the network.

Drag the arrow outside the circle. Clipping by norm shortens it to the circle along the same line. Clipping by value cuts it at the square, so for (1.9, 0.9) it turns from 25 to 42 degrees. The threshold is \(c\).

The answer to the guess is yes for clipping by norm, and the figure shows why: the update is the gradient times a number between 0 and 1. The idea comes from Pascanu, Mikolov and Bengio (2013), who proposed it for recurrent networks, where exploding gradients are common. The next figure uses the exploding run of the lab. The target is the shark's weight in kg with squared error, and the heaviest sharks (up to 58.6 kg) produce gradients far above the normal batch.

Without clipping, validation error ends at 1.78 kg², and the update ratio of layer 1 reaches 0.05 at times, 50 times the usual 0.001. With clipping at norm 1.0 the ratio stays between 0.0002 and 0.001 and the validation error is 0.13 kg². Same network, data and seed; one run per setting.

Where it misleads. Clipping treats the symptom. Another fix in the lab treats the cause. Predicting the log of the weight removes the heavy tail (as in A2), and the loss falls smoothly with no clipping at all. Its numbers are in log units, so compare the behaviour of the curves, not the values. A threshold that is too low acts like a smaller learning rate on all batches. In practice, log the norm before clipping and look at its distribution over a few hundred steps. Choose \(c\) a little above the typical norm so that only the extreme batches are cut. Why does clipping not hide a learning rate that is too high?

It caps the size of one step, but a rate that is too high also causes oscillation and dead units in steps below the cap. In the lab's NaN run the clipped network still stays at the base-rate loss.

The threshold test shows clipping at \(c = 30\) ending worse than no clipping. What should you do before you conclude that high thresholds hurt?

Repeat the test with several seeds. The result is one run, and seed-to-seed spread is large (the reproducibility section). With seeds 0 to 4 the median error at \(c = 30\) is 1.2, against 4.1 with no clip. Also log how often the clip fires, because a threshold that never fires and one that fires on most steps are different faults.

A learning-rate range test

Guess first. You train for 200 steps while the learning rate rises from 0.00001 to 3. The loss falls, reaches a lowest point, then blows up. Where would you choose the rate for a long run: at the lowest point, well before it, or after it?

learning-rate range test
a short run in which the rate rises step by step while the loss is recorded
smoothed loss
the loss averaged over the last few steps, so that batch noise does not hide the trend (0.7)
divergence point
the rate where the loss rises above its starting value

The range test finds the rates at which the loss falls and the rate at which it breaks, so you can choose a rate before a long run.

The loss is nearly flat below 0.0003, falls steeply from 0.003 to 0.03, is lowest near 0.07 and rises again above 0.4. Rates of 0.003 and 0.01 give the best validation loss (0.65 and 0.68), and rates of 0.3 and above stick between 1.2 and 1.3. Click the left plot or use the slider to see the training run for ten fixed rates. SGD with momentum 0.9 on the 480 made-up records, one seed.

The answer to the guess is "well before". The lowest point of the range test is reached while the rate is still rising, so the network has not had time to settle at that rate. The common rule is to take a rate about ten times below the lowest point, here 0.007. The runs on the right agree. Validation loss at 0.003 is 0.65, at 0.01 it is 0.68, and at 0.1 it is 0.84 (a rate near the lowest point of the test). At 0.3 the run has died (loss 1.23). Smith (2017; first posted in 2015) described the test in the paper on cyclical learning rates, as a way to find the bounds of a good range.

Two ways to read the curve. The first rule takes a tenth of the rate at the lowest smoothed loss. That loss is 0.71 at a rate of 0.071, so the rule gives 0.007. The second rule takes the rate where the loss falls fastest per tenfold rise of the rate. The code below finds it near 0.023, where the smoothed loss falls by 1.2 per tenfold rise (the figure's own run puts it near 0.018, because its batch order differs). Compare both with the fixed-rate runs. The validation loss is 0.65 at 0.003, 0.68 at 0.01 and 0.77 at 0.03. The first rule gives a rate between the two best rates, 0.003 and 0.01. The second gives one between 0.01 and 0.03. Both are in the good band. Neither rate was run itself. The first lies between the two best runs. The second lies between the runs with losses 0.68 and 0.77. So the first looks safer, though another seed could change the order.

The ramp itself has a meaning. The rate rises by 6.5% per step. It takes 73 steps to go from \(10^{-5}\) to \(10^{-3}\), more than a third of the run, and the loss hardly moves there. The lowest point comes at step 140, which is where \(10^{-5}\times1.065^{140} = 0.07\). The useful part of a 200-step test is the last 100 steps.

# continues the lab code above
def range_test(lo=1e-5, hi=3.0, steps=200, batch=32):
    net = network()
    opt = torch.optim.SGD(net.parameters(), lr=lo, momentum=0.9)
    g = torch.Generator().manual_seed(0); order = torch.randperm(480, generator=g); pos = 0
    rates, smooth, ema = [], [], None
    for t in range(steps):
        lr = lo * (hi / lo) ** (t / (steps - 1))                  # the rate rises by the same factor at every step
        for group in opt.param_groups: group["lr"] = lr
        if pos + batch > 480: order = torch.randperm(480, generator=g); pos = 0
        i = torch.tensor(tr)[order[pos:pos + batch]]; pos += batch
        opt.zero_grad(); loss = nn.functional.cross_entropy(net(X_std[i]), y[i]); loss.backward(); opt.step()
        ema = loss.item() if ema is None else 0.9 * ema + 0.1 * loss.item()       # smoothed loss
        rates.append(lr); smooth.append(ema)
    return np.array(rates), np.array(smooth)

\[ \eta_t \;=\; \eta_{\min}\Big(\frac{\eta_{\max}}{\eta_{\min}}\Big)^{t/T} \]

  • \(\eta_t\) is the rate at step \(t\), \(T\) the number of steps of the test (199 intervals for 200 steps), and \(\eta_{\min}\), \(\eta_{\max}\) the first and last rates. Equal steps on a log scale make the curve readable on a log axis.

Where it misleads. The best rate for a long run is often lower than the rate that is fastest in the first 200 steps. It changes with the batch size, with warm-up and with the schedule (B5). The loss curve of the test is noisy with small batches, hence the smoothing, and the lowest point moves from seed to seed. In practice, run the test once for a new model or data set, starting from the initial weights. Stop when the loss is more than about four times its best value. Treat the result as a bracket of rates to try, and try a rate near the middle of the bracket first.

Debug tip. If the loss stays flat for the whole range test, even at a rate of 1, check two things. The optimiser must be updating the weights (the update ratio is not 0), and the loss must be connected to the model's output.

Quick quiz

Why is the range test's lowest point not the rate to use?

The loss at a rate was measured while the rate was rising and the weights were still near the start. A rate that is best for 200 steps on a ramp is often too high to stay stable for thousands of steps. A tenth of it is a safer first try.

With the ramp of the worked example, at which step is the rate 0.07, and why does the lowest loss come after the steep fall?

The rate is \(10^{-5}\times1.065^{t}\), so \(t = \ln(7000)/\ln(1.065) = 140\). The loss falls while the rate is useful and bottoms out when the steps get too long to settle. The smoothed value lags the rate by a few steps, so its lowest point comes a little after the best rate.

What would a range test with a loss that falls until the end of the ramp tell you?

The ramp stopped too early. Extend the top rate until the loss breaks, otherwise you know only the lower end of the good range.

Learning curves, bias and variance

Guess first. A species classifier has a training error of 25% and a validation error of 29%. Would 10 times more sharks help it a lot, a little or not at all?

learning curve
training and validation error plotted against the number of training examples
avoidable bias
the part of the training error above the best error you could hope for; fixed by a better model or better inputs
variance
the gap between validation and training error; fixed by more data, a penalty or a smaller model

The gap between the two curves says whether more data will help, and the height of the training curve says whether a bigger model will.

The too simple model has training error 0.25 and validation error 0.29 at 384 sharks: both curves are flat and above the target. The too flexible model has training error 0.00 and validation error 0.30, and its validation curve is still falling. The middle model has 0.18 and 0.26. Means of 10 networks on the made-up records; the validation set has 120 sharks. The target of 0.20 is a made-up working goal, close to the error of the trees of A5 and A6.

The answer to the guess is "not at all". Training error 25% and validation error 29% means the model is far from the target already on the sharks it has seen. More sharks would raise the training error and not lower it. This is Ng's argument in Machine Learning Yearning (chapters 20 to 32). The training error shows bias, and the difference between validation and training error shows variance. If the training error is already above the desired level, more data cannot repair that. Try the three models. In the flexible model the training error is 0 for all sizes while the validation error falls from 0.40 to 0.30 and has not stopped. Here more data helps, and so does a penalty or a smaller network.

Ng's decomposition takes the best achievable error (his "optimal error rate") into account. Total error is optimal error plus avoidable bias plus variance. Avoidable bias is training error minus optimal error, and variance is validation error minus training error. In the figure the target of 0.20 replaces the optimal error. For the simple model at 384 sharks, the avoidable bias is \(0.25 - 0.20 = 0.05\) and the variance is \(0.29 - 0.25 = 0.04\). Both are modest, and the model is limited by its inputs. It uses the length only, while the other models also see girth, weight, depth and month. For the flexible model the avoidable bias is 0 (training error is below the target) and the variance is 0.30. The remedies are short. For high avoidable bias, try a bigger model, new inputs, or longer training. For high variance, try more data, a penalty (B7), augmentation, or a smaller model.

The other two models by the numbers. The simple model improves from 0.358 to 0.291 as the data grows from 12 to 48 sharks, then stays between 0.291 and 0.294 up to 384. Eight times more sharks changed the validation error by 0.003, and its training error is already 0.25. This is the case of the guess: it needs a better model or new inputs. For the medium model, the validation error falls by 0.027 from 96 to 192 sharks (0.304 to 0.277) and by 0.019 from 192 to 384 (to 0.258). The gains shrink as the data doubles. If the next doubling gave about 0.013, the error would be near 0.245, still above the target of 0.20. That is an extrapolation and not a measurement, but it says that more data alone will be slow.

In practice, plot the curve before collecting more data, because collecting is expensive and the curve is cheap.

A model has training error 0.02, validation error 0.22, target 0.10. Avoidable bias and variance? What would you try first?

Avoidable bias 0 (0.02 is below the target); variance \(0.22 - 0.02 = 0.20\). Try more data, a weight penalty, augmentation, or a smaller model.

Why does the training error rise as you add data for the flexible model?

With 12 sharks a large network can memorise all of them. With 384 it cannot fit all noise, so training error rises slightly (0.002 at 384). Ng notes that training error usually rises as the training set grows.

A model has training error 0.30 and validation error 0.32, and the target is 0.10. The last doubling of the data lowered the validation error by 0.001. What do you try?

Guess first. You train the same network twice with two learning rates, 0.02 and 0.03, and the second run scores 1 point higher on validation. Is 0.03 better?

A difference smaller than the spread between seeds is not evidence, so change one thing, run several seeds and compare in pairs.

With 20 seeds, rate 0.02 averages 72% and rate 0.03 averages 71%. The spread across seeds is 4 points, and the paired difference is −0.5 ± 1.4 points, so there is no sign of a difference. The same network, data and settings; only the seed (initial weights and batch order) changes. Switch to the paired view to see the 20 lines.

The answer to the guess is "not yet". The spread between seeds is 4 points, so a single pair of runs can differ by 1 point or by 8 and tell you little. The paired comparison cancels what the two settings share. For a seed, take the difference, and look at the average of the differences with an interval of \(\pm 1.96\) standard errors (0.7). Here the mean difference is \(-0.5\) points and the standard deviation of the differences is 3.2 points. With 20 seeds the standard error is \(3.2/\sqrt{20} = 0.72\), so the interval is \(-0.5 \pm 1.4\). It contains 0. The paired interval, step by step, and how many seeds you need. The code below takes the 20 scores of both rates and subtracts them seed by seed. The differences have a mean of \(-0.5\) points and a standard deviation of 3.18, so the standard error is \(3.18/\sqrt{20} = 0.71\) and the 95% interval is \(\pm 1.4\). Treating the two groups as unrelated gives a standard error of 1.29, because that keeps the seed-to-seed spread which pairing removes. The same 20 seeds give an interval 1.8 times narrower when they are paired. To see a gain of \(\delta\) points you need an interval narrower than \(\delta\). That means \(1.96\,s/\sqrt n \le \delta\), so \(n \ge (1.96\,s/\delta)^2\). With \(s = 3.2\) that is at least 5 seeds for a 3-point gain and 10 for a 2-point gain. These counts are floors. With so few seeds the multiplier 1.96 should be a t-value (2.8 for 5 seeds), which raises them to 7 and 13. A gain equal to the half-width of the interval is also found only about half the time.

Where it misleads. Seeds do not make a run reproducible on another machine. Some GPU operations are not deterministic, data loaders that use several workers can change the order, and library versions change the numbers. PyTorch has an option to ask for deterministic algorithms, at a cost in speed. Twenty seeds is also a lot for a large model. In practice: log the seed, the settings and the code version of a run. Change one setting at a time. Use at least 3 to 5 seeds for any comparison whose effect is a few points. Report the spread and not the best run. Selecting the best of many seeds and reporting it is a form of peeking at the validation set (A4).

Quick quiz

Two settings differ by 2 points with a seed spread of 4 points and 3 seeds per setting. Do you accept the difference?

No. With 3 seeds the standard error of a mean is about \(4/\sqrt3 = 2.3\) points, so a 2-point difference is within the noise. Run more seeds, or pair them.

Why is the paired comparison tighter than comparing two means?

A pair shares the seed, so luck that helps both runs, such as a good initial draw, cancels in the difference. The spread of the differences (3.2 points) is then smaller than the spread of the scores combined.

Two settings differ by 3 points on average over 5 paired seeds, and the differences have a standard deviation of 3.2. Give the 95% interval. Is the gain shown?

The standard error is \(3.2/\sqrt5 = 1.43\). With the multiplier 1.96 the interval is \(3 \pm 2.8\), from 0.2 to 5.8. For 5 seeds the right multiplier is the t-value 2.78, which gives \(3 \pm 4.0\), from \(-1.0\) to 7.0. It contains 0, so the gain is suggested and not shown. Run more seeds.

One more detail is not a bug of the four. The standardising step uses the mean and spread of all 600 rows, validation rows included. That is a small leak of the kind A4 describes. It does not matter here, but a careful pipeline computes them on the training rows only.

Six of the eight tests fail. Five of them point at a specific bug, and between them they name all four. The two that pass, the starting loss and the array sizes, are the ones that all four bugs get past. The outputs are from running the code above; the pipeline's numbers are 0.450 buggy and 0.750 fixed on 120 validation sharks.

The answer to the guess is four: the data check (bug 1), the gradient test (bug 3), the evaluation-mode test (bug 4) and the output print (bug 2). The overfit test also sees bugs 2 and 3, but it cannot say which is which. The tests were chosen so that a test looks at one component. The data test reads the input and its label. The starting-loss test reads the model and loss together. The overfit test reads the whole loop on a tiny batch. The gradient test isolates backward and zero_grad, the mode test isolates dropout, and the output print isolates the last layer. Tick them in any order. The lazy-baseline test says that the model has learned no more than a guess, and not why. That is the usual value of a baseline: it tells you whether to keep looking.

Fix the bugs one at a time, and test again after a fix. The scores after the fixes are worth seeing. Fixing the shuffle gives 0.55. Removing the softmax as well gives 0.06, because the missing zero_grad now lets the gradients grow without limit. Adding zero_grad gives 0.77, and switching to evaluation mode gives 0.75. A fix can make the score fall before it rises, because it uncovers a bug that was hiding behind another. This is the practical reason for the one-component-at-a-time rule: with four changes at once you would not know which one helped.

One bug at a time. A second experiment puts one bug at a time back into the repaired pipeline. Validation accuracy is 0.450 with only the two separate shuffles, the lazy model, so that bug alone ends learning. With only the missing zero_grad it is 0.433. With only the double softmax it is 0.775, and with only the dropout left on during validation it is 0.767, against 0.750 for the repaired pipeline. The last two stay inside the range of the six network seeds above (75.0% to 80.0%), so no accuracy check would find them. The tests do, because a test reads one component. A bug that leaves the score alone on this data can matter elsewhere. The double softmax squeezes the scores into the range 0 to 1, which flattens the loss, and dropout during validation adds noise to all the numbers you compare. Starting from the broken pipeline, fixing a single bug raises the score only for the shuffle (0.55).

Common belief. If the starting loss matches \(\ln K\) and the code runs without errors, the pipeline is correct.

Why it fails. The starting loss only checks the model and loss at initialisation. The shuffled labels, the missing zero_grad and the dropout in evaluation do not change it, and none of them raises an error.

Better account. A check covers one component, and a pipeline is trusted only when the components have passed their own checks, including the one that reads a known example.

Debug tip. Write a test once as a short function and keep it with the code. The overfit-one-batch test and the check of one known shark take a minute to run and find most bugs of this kind.

Quick quiz

Which two tests would have caught the label bug before any training?

Reading one known example (Tag 5519) and its label, and a lazy-baseline comparison after a short run. The first catches it directly.

The softmax bug did not change the starting loss. Why?

The outputs after the first softmax are close to 0.2, and a second softmax of numbers near 0.2 is still close to uniform. The loss starts near \(\ln 5\) either way.

The double softmax alone leaves the accuracy at 0.775, above the repaired pipeline. Why is it still worth fixing?

It squeezes the scores into the range 0 to 1, so the loss is flat and the slopes are small. With five classes the second softmax gives the true class at most \(e/(e+4) = 0.40\), so the loss cannot fall below 0.90. Training is slower and the printed probabilities are not what the loss treats as scores. Here the data is easy enough to hide this, and a harder problem would not.

(b) A model predicts the class shares 0.5, 0.3, 0.15 and 0.05 for all sharks, and the labels have those shares. What is its loss? (b) How many steps does it take to change the layer by its own norm if the gradient stayed constant in size? (c) If the optimiser uses momentum 0.9 and the gradient has a constant direction, how does the steady ratio change?

    Hint

    With momentum \(\beta\) and a constant gradient the velocity grows to \(1/(1-\beta)\) times the gradient.

Come back later

(B4, B8) A twelve-layer sigmoid network has a gradient of size 7.5e-8 reaching layer 1 and about 0.2 at layer 12. Which number of the lab shows this, and what does the update ratio of layer 1 look like?

The gradient norm per layer, which falls by the factor 0.227 per layer of B4 across 12 layers. The update ratio of layer 1 is tiny, like the 3.7e-7 of the badly initialised lab run, so layer 1 barely learns. The cure is in B6: a better initial scale, normalisation or shortcuts.

(A4, B8) A learning curve shows validation error flat at 0.29 while training error falls from 0.25 to 0.0. What do you conclude about the model and what do you try?

The model is memorising: variance is large. Try more data, a weight penalty or augmentation (B7), or a smaller network, and use early stopping with the validation curve.

(B5, B7, B8) After fine-tuning on a new water the validation score is good. Which two checks of this chapter and B7 should you also run?

Score the old water's held-out set again, to catch forgetting (B7). Compare with a lazy baseline and a few seeds, so that a good score is not noise or chance (B8).
